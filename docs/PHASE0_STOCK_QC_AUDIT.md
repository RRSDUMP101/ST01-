### 6.2 แบบข้อมูลที่เสนอ

ไฟล์ใหม่ `stock.sqlite3` ใน data directory (ใช้ `sqlite3` ของ Python ไม่เพิ่ม dependency) — ทางเลือกนี้ใช้ได้เมื่อคำตอบ ค-2 คือ "คอมหลักเครื่องเดียวเขียน"; ถ้าหลายเครื่องเขียนพร้อมกันต้องเปลี่ยนเป็นบริการกลาง/เซิร์ฟเวอร์ฐานข้อมูล

| ตาราง | คอลัมน์หลัก | หมายเหตุ |
| --- | --- | --- |
| `items` | `item_key` (PK = `_key(code)`), `code`, `name`, `base_unit`, `express_code`, `count_code`, `track_lot` (ปิดไว้) | ทะเบียนสินค้าแยกจากยอด |
| `item_units` | `item_key`, `unit`, `factor_to_base` | ไม่มีตัวคูณ = บันทึกไม่ได้ |
| `warehouses`, `bins` | `wh_code`; `wh_code + bin_code` | `bins` นำเข้าจาก `Catalog.locations`/ผังชั้นวางเดิม |
| `balances` | PK (`item_key`, `wh_code`, `bin_code`, `quality_status`='available', `lot`=''), `qty`, `updated_at` | `CHECK (qty >= 0)` ยกเว้นมีข้อยกเว้นที่อนุมัติ |
| `documents` | `doc_no` PK, `doc_type` (PD/OU/FR/RR/AJ/TR), `status`, `request_id` UNIQUE, `payload_hash`, `job`, `express_no`, `created_by/at`, `posted_by/at`, `reverses_doc_no`, `reason` | `request_id` คงอยู่หลัง restart |
| `document_lines` | `doc_no`, `line_no`, `item_key`, `wh_code`, `bin_code`, `to_wh`, `to_bin`, `qty`, `unit`, `base_qty`, `unit_cost`, `remark` | |
| `movements` | `id`, `doc_no`, `line_no`, `item_key`, `wh_code`, `bin_code`, `quality_status`, `lot`, `qty` (หน่วยหลัก ±), `balance_after`, `at`, `by`, `reversal_of` | ไม่มีการแก้/ลบ มีแต่รายการกลับ |
| `negative_overrides` | `doc_no`, `line_no`, `approved_by`, `reason`, `at` | |
| `schema_meta` | `version` | migration แบบเพิ่มต่อท้ายเท่านั้น |

ใบโอน `TR`: บันทึกครั้งเดียว = ออกจากต้นทางเข้า "ระหว่างทาง" (`wh_code = 'TRANSIT'`) ในธุรกรรมเดียว; รับปลายทาง = เอกสารรับที่อ้างใบโอน; ยกเลิก = รายการกลับที่อ้างต้นฉบับ

### 6.3 ขั้นตอนบันทึกเอกสาร (ทุกช่องทาง: คอม, มือถือ, หน้าสต็อกเหล็ก)

1. `BEGIN IMMEDIATE` (ล็อกการเขียนทั้งฐาน — สองคำขอเบิกชิ้นสุดท้ายจะเข้าทีละรายการ)
2. ถ้ามี `request_id` เดิม: payload ตรงกัน → คืนผลเดิม, ไม่ตรง → ปฏิเสธ
3. ตรวจทุกบรรทัด: รหัสมีในทะเบียน, หน่วยมีตัวคูณ, จำนวน > 0 (AJ ±), คลัง/ช่องเก็บมีจริง, ยอดพร้อมเบิกพอ (ยกเว้นมี override)
4. มีข้อผิดพลาดแม้บรรทัดเดียว → `ROLLBACK`, เอกสารยังเป็น "ร่าง", คืนรายการข้อผิดพลาดต่อบรรทัด
5. ผ่านทั้งหมด → ปรับ `balances` + เขียน `movements` + ตั้งสถานะในธุรกรรมเดียว → `COMMIT`
6. UI แสดงผลตามผลธุรกรรมจริง (สำเร็จ/ไม่สำเร็จพร้อมเหตุผลต่อบรรทัด) ไม่แสดง "บันทึกแล้ว" เมื่อไม่ได้บันทึก

### 6.5 แผนย้ายข้อมูล (ยังไม่รันกับข้อมูลจริง)

1. **สำรอง:** คัดลอก data directory ทั้งโฟลเดอร์ (library.json, mobile.json, images, sale_bridge.sqlite3 ถ้ามี) พร้อม SHA-256 และ **ทดลองกู้คืนลงเครื่องทดสอบให้เปิดได้ก่อน**
2. **Dry-run บนสำเนา:** อ่าน library.json → `items`, `bins`, `balances` (ยอดปัจจุบันของแต่ละรหัสลงคลัง/ช่องเก็บตามคำตอบ ค-3), เอกสาร/ประวัติเดิมนำเข้าเป็นประวัติ (คลัง = `LEGACY`), ตัวนับเลขที่
3. **รายงานกระทบยอด:** ยอดรวมต่อรหัสก่อน = หลัง, จำนวนเอกสาร/ประวัติเท่ากัน, รหัสซ้ำต่างแหล่ง (ค-9), หน่วยที่ไม่มีตัวคูณ, รหัสที่ไม่มีคลัง — ทุกข้อขัดแย้งต้องมีคนตัดสิน ไม่เลือกอัตโนมัติ
4. **ตัดยอดกลุ่มทดลอง:** หยุดบันทึกชั่วคราว → สำรองครั้งสุดท้าย → ย้าย → ตรวจรายงาน → เปิดสวิตช์กลุ่มทดลอง
5. **ย้อนกลับ:** ปิดสวิตช์ + กู้ library.json จากสำรอง; เอกสารที่บันทึกหลังตัดยอดส่งออกเป็นรายการให้คีย์ซ้ำ (ไม่มีการลบประวัติ)
