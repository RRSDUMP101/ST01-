# RRS Stock & QC (เว็บ)

ระบบสต็อก–จอง–จัดซื้อ–QC ตามแผน Phase 0–6 (`docs/PHASE0_STOCK_QC_AUDIT.md` และเอกสาร "RRS QC" ใน Google Drive)
สร้างเป็นหน้าเว็บไฟล์เดียว ใช้ได้ทั้งเป็น Artifact แบบส่วนตัวใน claude.ai และขึ้น Cloudflare Pages ในภายหลัง

> สถานะ: **ระบบต้นแบบครบทุกเฟสสำหรับทดลอง (UAT)** ยังไม่เชื่อม Google Sheet / Cloudflare และยังไม่ได้ใช้กับข้อมูลจริง
> ผลทดสอบอัตโนมัติผ่านแล้วไม่ได้แปลว่าผ่านการตรวจรับของสโตร์/QC/บัญชี — ใช้หน้า "ทดสอบรับงาน (UAT)" บันทึกผลจริง

### หลักการที่ทำให้ยอดถูกต้อง

- ทุกคำสั่งตรวจครบก่อน แล้วได้ **commit เดียว** ที่มีทุกแถวที่เปลี่ยน — มีบรรทัดผิดบรรทัดเดียว ไม่มีอะไรเปลี่ยน
- commit เรียงลำดับ (seq) และต่อกันด้วย SHA-256 (`prev` → `hash`) แก้ย้อนหลังแล้วตรวจพบ
- คำขอทุกครั้งมี `requestId` ส่งซ้ำ (กดซ้ำ/เน็ตหลุด/เปิดโปรแกรมใหม่) มีผลครั้งเดียว
- บันทึกได้ทีละรายการ: ถ้ามีคนบันทึกก่อน คำสั่งถูกตรวจใหม่บนข้อมูลล่าสุด (สองคนเบิกชิ้นสุดท้าย สำเร็จคนเดียว)
- ยอด = ผลรวมประวัติเสมอ (`RRS.inventory.verifyBalances`), ยกเลิก = รายการกลับ ไม่ลบประวัติ
- ยอดแยก สินค้า + คลัง + ช่องเก็บ + สถานะคุณภาพ (ใช้ได้/รอตรวจ/กักกัน/รอแก้ไข) + ล็อต — ของรอตรวจ/กักกันเบิกไม่ได้

## โหมดข้อมูล (เลือกที่ปุ่มบนแถบด้านบน)

| โหมด | เก็บที่ | ใช้เมื่อ |
| --- | --- | --- |
| ข้อมูลตัวอย่าง | เบราว์เซอร์ของผู้เปิด (localStorage) | ทดลอง/อบรม สลับผู้ใช้ทดลองได้ ข้อมูลตัวอย่างรหัส `DEMO-…` |
| ข้อมูลทีม | ฐานข้อมูลร่วมของ Artifact (claude.ai) | ทีมใช้ร่วมกันระหว่างทดลอง ผู้ใช้ผูกกับบัญชี claude.ai ผู้เปิดคนแรกเป็นผู้ดูแล |
| เซิร์ฟเวอร์ | Cloudflare Worker + Google Sheet | ใช้จริง (ยังไม่ได้ทำ – ดูหัวข้อถัดไป) |

ข้อจำกัดโหมดข้อมูลทีม: เป็นต้นแบบ — โปรแกรมในเบราว์เซอร์ของแต่ละคนเป็นผู้ตรวจคำสั่ง (เชื่อ client) และฐานข้อมูลของ Artifact
เก็บได้ราว 25,000 commit / 256 KB ต่อ commit เหมาะกับการทดลองกลุ่มเล็ก ใช้งานจริงควรย้ายไปโหมดเซิร์ฟเวอร์

## ขึ้น Cloudflare (ส่วนที่ยังไม่ได้ทำ)

1. **หน้าเว็บ**: `node build.mjs` แล้วอัปโหลด `dist/index.html` เป็น Cloudflare Pages (static) — ใช้โหมดข้อมูลตัวอย่างได้ทันที
2. **เซิร์ฟเวอร์**: Cloudflare Worker ที่ `import` ไฟล์ใน `src/engine/` (ลำดับตาม `order.json`) แล้วเป็นผู้บันทึกคนเดียว
   - ใช้ **Durable Object** หนึ่งตัวต่อหนึ่งบริษัท/พื้นที่ เป็นตัวเรียงคำสั่งทีละรายการ (แทนการล็อกในเบราว์เซอร์)
   - API ที่หน้าเว็บเรียก (`RemoteLedger` ใน `src/store/stores.js`):
     - `POST {api}/command` body `{kind, payload, requestId}` → ผลแบบเดียวกับ `RRS.core.prepare` (`{ok, commit}` / `{ok:true, duplicate:true}` / `{ok:false, errors}`)
     - `GET {api}/commits?after=N` → `{commits: [...]}`
   - ผู้ใช้: ใส่ **Cloudflare Access** (เข้าด้วยบัญชี Google ของบริษัท) แล้ว Worker อ่านอีเมลจาก header ของ Access
     ไปเทียบกับ `users.accountId` — อย่าเชื่อชื่อผู้ใช้ที่ส่งมาจากเบราว์เซอร์
   - สร้างหน้าเว็บที่ชี้เซิร์ฟเวอร์: `RRS_API=https://<worker>/api node build.mjs`
3. **Google Sheet ใน Google Drive** (ผ่าน Google Cloud service account)
   - แท็บ `commits` คือข้อมูลหลัก: หนึ่งแถวต่อ commit (`seq, at, by, kind, summary, requestId, hash, prev, json`)
     ช่องเดียวของ Sheet เก็บได้ 50,000 ตัวอักษร — commit ที่ยาวกว่านั้นให้แบ่ง JSON หลายคอลัมน์ หรือเก็บเป็นไฟล์ใน Drive แล้วใส่ลิงก์
   - แท็บอื่น (`items`, `balances`, `documents`, `movements`, …) เป็นมุมมองให้คนอ่าน สร้างใหม่จาก commits ได้เสมอ
     หัวคอลัมน์ภาษาไทยดูได้ที่หน้า "พจนานุกรมข้อมูล / Google Sheet" ในโปรแกรม (ดาวน์โหลดเป็น CSV/JSON ได้)
   - คีย์ service account เก็บเป็น **Worker secret** (`wrangler secret put`) ห้ามใส่ใน repo / หน้าเว็บ / Sheet
   - Google Sheets API มีโควตาจำนวนคำขอต่อนาที — Worker ควรรวมการเขียนแท็บมุมมองเป็นชุด และเขียน `commits` ก่อนเสมอ
   - สำรอง: ใช้ประวัติเวอร์ชันของ Sheet + ส่งออก commits เป็นไฟล์ JSON ใน Drive ตามรอบ แล้วตรวจด้วยหน้า "สำรองและกู้คืน"
4. ค่าเริ่มต้นของ staging: ไม่มีการส่งข้อความ/อีเมลอัตโนมัติ และไม่ใช้ข้อมูลจริงจนกว่าจะผ่าน UAT และได้อนุมัติ
